## 7. 検証で判明したギャップ（独立レビュー所見）

作成者のテストケースをレビューした結果、以下の未カバー観点を確認した。いずれも今回の合否判定を覆すブロッカーではないが、報告書側で明記する。

1. **`useTextAssetContent`フック自体の単体テストが無い**（`textAssetPreview.ts`）。`excerptFromMarkdown`はテスト済みだが、fetchキャッシュ（`contentCache`）・同時リクエストの重複排除（`inFlight`）・アンマウント後の`cancelled`ガードといったこのフックの中核ロジックは、`GalleryPanel`/`MediaPreview`経由の統合的な描画では明示的に検証されていない。
2. **`markdownLite.tsx`に専用テストが無い**（本書§4で独立に補完。ヘッダーが`<h1>`/`<h2>`を一切出力せず`<h3>`起点になる点、深度4〜6が全て`<h6>`に収束する点は、テストが無ければ気づきにくい実装依存の挙動である）。
3. **`_resolve_batch_info`のフォールバック経路（`batch_lookup=None`のとき`find_by_job_id`を都度呼ぶパス）は`list_gallery`からは常に`batch_lookup`を渡すため到達しない**。関数シグネチャ上は再利用可能だが、現状の呼び出し経路では単体テストされていないデッドパスに近い。将来`_serialize_gallery_item`が単独呼び出しされる箇所（例: `/gallery/{asset_id}`直接取得や`/job/{job_id}`系エンドポイント）で`batch_lookup`を渡し忘れた場合の検知手段が無い。
4. **ブラウザでの目視確認（実際のMarkdownレンダリング崩れ、サムネイル抜粋の折り返し、CSS `text-preview`/`gallery-item--nested`等のレイアウト）は本検証の範囲では未実施。** `npm run build`による型・ビルド成功の確認と自動テストの合格までを本検証のスコープとし、視覚的な最終確認は人間によるレビューを推奨する（検証報告書§5）。

これらは「合格/不合格」の判定基準においては不合格理由に含めない（自動テスト・独立検証はいずれもPass）が、今後の追加テスト候補として検証報告書に記載する。
